1. Introduction
1.1 Purpose
The purpose of this System Design document is to translate the business requirements and business processes defined in the SRS into a technical design that will be used to develop the LLM-Based Support Bot for the Ethiopian Revenue Authority. This document describes the system architecture, subsystem decomposition, and detailed object models required to implement the advanced Retrieval Augmented Generation (RAG) system with hybrid search capabilities.
This version (v1.1) incorporates implementation amendments from the Awaqi development phase. Where original and amended content conflict, the amendment takes precedence as documented in the SDS Amendment Overview section.
1.2 General Overview
The system is designed as an AI-powered information desk agent accessible via web interface and Telegram bot, capable of answering tax-related queries in Amharic and English. Unlike generic RAG implementations, this system employs a hybrid retrieval architecture combining BM25-style keyword matching with dense vector search (via PostgreSQL + pgvector), specifically optimized for Ethiopian tax terminology and Amharic language processing.
The system operates by:
1. Ingesting regulatory documents from the Ministry of Revenue (MoR) website.
2. Converting documents into vector embeddings using Gemini embedding models (3072-dim). [Amended — see SDS-CHG-02.]
3. Implementing dual retrieval paths (dense + sparse FTS) with Reciprocal Rank Fusion.
4. Using a Large Language Model (Gemini) to generate regulation-grounded responses with mandatory citations.
5. Applying confidence scoring to prevent hallucinations and trigger appropriate fallbacks.
1.3 Development Methods & Contingencies
Methodology: The system design utilizes Object-Oriented Design (OOD) principles to model the interaction between Users, Documents, and the Chat Engine. Development follows an Agile approach with iterative sprints, allowing for rapid adjustment of LLM prompts and retrieval parameters.
Implemented Technology Stack: [Amended per SDS-CHG-01 through SDS-CHG-06]
6. Backend: Python FastAPI + SQLAlchemy async + Alembic
7. Frontend: Next.js (React with TypeScript) + next-intl
8. AI/ML — Orchestration: Custom orchestration in apps/api + packages/ai-engine
9. AI/ML — Generation: Gemini chat model (configurable)
10. AI/ML — Embeddings: Gemini embedding model (gemini-embedding-001, 3072-dim)
11. Database: PostgreSQL + pgvector extension
12. Cache / Rate Limiting: Redis
13. OCR / Extraction: PyMuPDF + Tesseract + HTML extraction
14. Deployment: Docker Compose (api, web, db, redis, telegram-bot)
Contingencies:
15. LLM Latency: If Gemini API experiences high latency (>5s), the design activates the extractive deterministic fallback path. [Amended from Llama/Ollama — see SDS-CHG-03.]
16. Scraper Blocking: If the MoR website changes its DOM structure, the Scraper module is isolated and can be updated independently without redeploying the core chat service.
17. Low Confidence Responses: If retrieval confidence falls below the threshold, the system returns a standardized fallback message rather than potentially hallucinated content.

2. System Architecture
2.1 Subsystem Decomposition
The system is decomposed into four major subsystems to ensure separation of concerns. [Amended from original per SDS-CHG-01 and SDS-CHG-06.]
2.1.1 Client Subsystem (Frontend)
* Responsible for rendering the chat interface, handling user input, and displaying responses.
* Web app: Next.js app-router with multilingual UX, admin surface, and chat interface.
* Telegram bot: Separate runtime forwarding to the same chat backend.
* Components: ChatUI, HistoryManager, APIConnector, AdminDashboard.
2.1.2 API Subsystem (Backend Controller)
* Acts as the central controller, managing session state and routing requests.
* FastAPI routers:
   * chat — send / history / export / feedback
   * admin — documents, ingestion, analytics, health, scraper controls
   * telegram_link — link-request / confirm / status / unlink
* Session token verification enforced for guest data access.
* Redis-backed request rate limiting.
2.1.3 Intelligence Subsystem (RAG Engine)
* Language detection: heuristic am/en/mixed detector.
* Retrieval:
   * Dense search on pgvector embeddings
   * Sparse keyword retrieval using PostgreSQL FTS candidate ranking
   * Reciprocal Rank Fusion (RRF, k=60)
* Generation:
   * Primary: Gemini chat generation
   * Fallback: Extractive deterministic synthesis
* Confidence: Heuristic score computed and returned; threshold gating deferred (see SDS-DEF-04).
2.1.4 Ingestion Subsystem (Data Pipeline)
* Ingestion flow:
   * Document extraction (HTML/PDF)
   * OCR fallback with confidence tracking
   * Token chunking
   * Embedding generation (Gemini, 3072-dim)
   * Atomic chunk replacement for re-index
* Document lifecycle statuses: pending, processing, indexed, failed, requires_manual_review.
* Scheduler: APScheduler-based configurable daily scraping.

5. Algorithm Design


  

Figure: End-to-End Algorithm Pipeline


  

State Chart Diagram: Hybrid RAG System Logic Tree


5.1 Hybrid Retrieval Augmented Generation (RAG) Flow
The system uses an advanced hybrid RAG pattern that combines keyword matching with semantic search.
18. Input: Query from user in Amharic, English, or mixed.
19. NLU Processing: Heuristic language detection → intent classification → entity extraction.
20. Dual Retrieval Path:
   * Dense Search: Cosine similarity on pgvector with Gemini embeddings (3072-dim). [Amended from multilingual-e5-large — SDS-CHG-02]
   * Sparse Search: PostgreSQL FTS keyword ranking for exact legal terms. [Amended from Elasticsearch — SDS-CHG-06]
   * Fusion: Reciprocal Rank Fusion (k=60) combines both result sets.
21. Confidence Check: If max retrieval score < threshold, return fallback message instead of proceeding.
22. Augmentation: User question + top-5 retrieved chunks → structured prompt with citation requirements.
23. Generation: Gemini primary model generates response with citations. Extractive fallback activates on failure. [Amended from Llama/Ollama — SDS-CHG-03]
24. Post-Processing: Citation validation; anonymized query-response pair logged; session context updated.
5.2 Reciprocal Rank Fusion (RRF)
Combines dense and sparse retrieval results into a unified ranking.
Formula: RRF_score(d) = Σ 1 / (k + rank_i(d))  where k = 60
Benefit: Documents appearing in top ranks of both systems receive the highest combined scores, leveraging strengths of both dense and sparse approaches.
5.3 Confidence Estimation
Multi-signal heuristic scoring to prevent hallucinations.
Signal
	Weight
	Measurement
	Retrieval Score
	0.4
	Max cosine similarity from dense pgvector search
	BM25 / FTS Score
	0.2
	Normalized PostgreSQL FTS score
	Citation Overlap
	0.3
	Ratio of generated claims with source support
	LLM Uncertainty
	0.1
	Token probability variance (where available)
	

Decision Logic:
* Combined Score ≥ 0.7 → Return answer with citations.
* Combined Score 0.5–0.7 → Return answer with disclaimer.
* Combined Score < 0.5 → Return fallback: 'Please consult an ERA officer directly.'
Hard threshold gating is a planned enhancement. Current implementation returns heuristic score as informational signal — see SDS-DEF-04.
5.4 Guest Rate Limiting (Token Bucket via Redis)
* Identifier: Client IP Address.
* Storage: Redis Cache (In-Memory, TTL 600 seconds).
* Logic: GET rate_limit:{IP} → if null: SET = 1, EXPIRE 600 → if < 15: INCR, allow → if ≥ 15: HTTP 429.
* Privacy: Redis key auto-expires after 10 minutes; no permanent IP log retained.
5.5 Text Chunking (Sliding Window)
* Chunk size: ~750 words (1024 tokens).
* Overlap: 100-word overlap between adjacent chunks for context continuity.
* Metadata preservation: Each chunk retains source document ID, page number, and section header for citation.
